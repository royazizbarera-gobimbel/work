# Taste
- For new proxy/BFF-level APIs and modules (e.g. go-superapp-api), request params/bodies are typed `any` with no DTO — except protobuf/gRPC-based endpoints, which must have DTOs. Applies project-scope to this workspace. Confidence: 0.85
- Keeps coding conventions in a repo `AGENTS.md` (workspace root) and treats it as the source of truth; prefer reading/following it rather than duplicating those rules into other config. Confidence: 0.6
- When the assistant lacks context (DB access/credentials, the symptom, which environment a host belongs to), prefers it just ask him directly instead of spelunking through repos/env files to guess; pushes back ("apa yang lu cari?? ngomong aja") on broad independent investigation. But once he points at the source (env file, sibling repo), dig there instead of asking again — he gets annoyed by repeated questions ("tuh kenapa sih masih nanya mulu ke gua??") and expects the assistant to extract already-available config (e.g. commented-out prod blocks in `.env`) itself. Confidence: 0.8
- When asked to "cek" an endpoint/behavior, trace it through the source code (controller → service → schema/DB) rather than curling the live API URL; corrects the assistant when it tries to probe the remote endpoint directly. Confidence: 0.6
- Before running any DB query, inspect the actual schema first (tables/columns/models); rejects blind queries against an unknown schema ("lu asal query tanpa tau gmna skema db nya"). Confidence: 0.75
- Verify schema/columns and data availability by querying the live database the current `.env` points at, not by reading `schema.prisma` snapshots off a git branch — when he has already repointed the env ("udah gua arahin ke beta"), he expects the assistant to check the real DB ("lu nelusurin by db kah?? coba cek"). Confidence: 0.7
- Workspace repo convention: each service's source (models/schema definitions, config) lives in its own sibling repo under the workspace root (e.g. `bp-online` code is in the `bp-online` repo) — look up a service's shape there first instead of asking or inferring from other repos ("bp online itu di repo bp-online sendiri masa gk tau sih"). Confidence: 0.55
- Verification of a finished change stops at the build (`npm --prefix … run build` → EXIT 0); don't start the local service and curl smoke-test the endpoints afterwards ("gk perlu lu curl bro, skillnya cuman sampe build doang untuk verif"). Confidence: 0.7
- Dislikes being interrupted by per-command permission prompts during investigation work; asks for blanket approval ("gk bisa kah bypass all aja gitu??") rather than approving shell/DB commands one at a time. Confidence: 0.55
- When he says "trace", he wants the concrete trace he asked for (where each response field comes from, the actual SQL producing the row, the call flow) — not a legacy/SO-migration audit verdict just because a repo has an audit skill; assumes the assistant is hallucinating scope when it reframes ("bukan itu yang mau dicari lol lu halu mulu") and expects the trace focus to be confirmed first. Confidence: 0.65
- Token/context economy matters: calls out wasteful work ("gua ngerasa lu boros banget tokennya") — expects targeted reads (grep -A/-B, offset/limit per function instead of whole large files), bounded/trimmed tool output (head/tail/head_limit), and short prose that doesn't restate what was just read or re-summarize findings. Confidence: 0.8
- Dislikes play-by-play narration between tool calls ("why u are so many talk behind me"); prefers near-silent execution with one short summary of the result rather than "I'll read X / found Y" commentary for each step. Confidence: 0.6
- Wants design decisions discussed and agreed before code is applied: stop and lay out the open choices/scope as a short discussion ("diskusi dlu", "diskusi aja") instead of pushing through a multi-repo change autonomously; opens threads on coding-pattern/best-practice questions expecting trade-off analysis, not an immediate refactor. Confidence: 0.8
- Only surface genuinely open decisions in those discussions — do not ask him to confirm implementation details already implied by the stated task ("untuk apa lu nanya itu?? kan ini cuman memverifikasi hak aksesnya aja"); decide the self-evident points yourself and ask about real unknowns only. Confidence: 0.7
- Don't assume he knows technical jargon/shorthand (e.g. "dedup"): when proposing a technique, explain it plainly and concretely (what actually changes, a real before/after example from the data) instead of naming it and moving on. Confidence: 0.55
- Normalize away legacy DB column prefixes (`c_`, etc.) in raw SQL and in the row types: alias every selected column to a clean domain name (`SELECT ck.c_nik AS nik`) and give TS types the same plain names, so the code is portable to the newer schema/staging-beta ("jangan pake prefix c_ gitu gitu, pake nama yang sesuai aja"). Confidence: 0.75
- Rejects hardcoded enumerations of DB values (e.g. a `CASE uk.cakupan WHEN 'CABANG' … WHEN 'SEKRE' …`) when the value set can grow — new types like `RAYON` are expected, so derive output generically from the stored value (`CONCAT_WS(' ', uk.cakupan, NULLIF(uk.nama_cakupan, uk.cakupan))`) instead of listing known cases. Confidence: 0.6
- When a field's business meaning/contract isn't confirmed yet by the business side (BisDev), leave it `null` rather than inventing a plausible mapping ("pendidikan_karyawan null in dlu, belum ada konfirmasi lebih lanjut dari bisdev"), and only implement the parts that are already decided. Confidence: 0.7
- Environment ↔ repo pairing: changes for `staging-beta` testing go in the newer repos (`api-superapps-v2` for the BFF/proxy, `db-go` on its `staging-beta` branch), while the older repo (`go-superapp-api`) stays for `main`/PROD; when an endpoint is added to the prod proxy, expects the same proxy implemented in the staging-beta repo too so it is testable. Confidence: 0.6
- Workspace environment convention: ports starting `700x` are production here; per-service `.env` files (e.g. `bp-online/.env`) hold both prod and staging config, with staging URLs messy — so check the env file to determine which environment a host/port belongs to. Confidence: 0.7
- Progress/DSM reports: a task's "Yang dikerjakan" points accumulate across days — when updating a multi-day ticket, carry over the previous day's work points too, and don't file internal meta-work (e.g. creating a skill) as its own report task. Confidence: 0.55
- For a brand-new feature, don't build backwards-compat fallback chains: pick the one correct primary source (e.g. `unit_kerja.cakupan_id`) and drop the stale alternative entirely ("jangan pake fallback bro … jadi full yang baru aja, toh ini menu baru kok") instead of layering primary→fallback resolution. Confidence: 0.7
- Seed/config data (new master-grup rows, item inserts) should be handed over as a SQL script he runs himself ("buat pake sql aja nanti gua masukin ke db"), not executed by the assistant. Confidence: 0.6
- Preserve the codebase's existing error-handling convention rather than "upgrading" it: in `db-go` keep `throw new CustomError(msg, HttpStatus.X)` and do not swap in Nest built-ins like `HttpException`/`BadRequestException` ("pertahankan implementasi CustomError, kenapa lu selalu ubah ke HttpException??"). Confidence: 0.85
- When he asks a question ("kenapa…??"), answer the question itself — the actual root cause/reasoning — instead of just applying the fix or apologizing and moving on; he will call it out ("gua kan nanya kenapa?? jawab lah"). Confidence: 0.7
- Do not collapse/dedupe rows that merely look identical: when rows differ in hidden IDs (e.g. different `c_id_penempatan` / `c_id_pejabat_atasan`), show every row as-is ("jangan di dedup … tampilin aja gausah di dedup") instead of aggregating to a "cleaner" list. Confidence: 0.6
